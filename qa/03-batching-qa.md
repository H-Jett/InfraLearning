# 第 3 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 3 章 3.7 思考题》。

## 1. batch 上限该设在哪一档？

**参考答案**：设在**拐点附近、512 那一档左右**，不要冲到 1024。

理由：512 → 1024 是典型的"越过拐点"——吞吐只多 1.26×，每个用户的 TPOT 却从 18.9 ms 恶化到 30 ms
（涨 60%）。这笔买卖不划算：牺牲了所有在线用户的延迟体验，只换来一点点吞吐。工程上应在**延迟仍满足
SLO** 的前提下把 batch 往拐点靠，而不是一味追求最大吞吐。具体取哪一档，取决于业务的延迟目标：
延迟敏感就往 256/512 靠，离线批处理（不在乎延迟）才可以冲到 1024 甚至更高。

## 2. static batching 浪费率为什么能到约 50%？continuous 靠什么收回来？

**参考答案**：因为 static batching 必须等**最长的那条**（255）结束整批才算完，而其余序列平均只有
一半多长度就生成完了，却要占着槽位空转陪跑。数值上：有用 4110 token-步，却计算了 32×255=8160 步，
浪费 4050（≈49.6%）。

continuous batching 靠**以 decode 步为粒度的调度**收回来：某条序列一旦生成完就**立即退出、释放槽位**，
等待队列里的新请求**立即补进**这个空位一起算。于是短序列不再空转陪跑，GPU 始终在做有用功——把这
~50% 的浪费变回有效吞吐。

## 3. continuous batching 给 KV cache 显存管理带来什么麻烦？

**参考答案**：序列不断进进出出、每条长度还都在动态增长，于是 KV cache 需要**随时按需分配和释放**
一块块大小不一的显存。如果按"最大长度"给每条序列预留连续显存，会产生严重的**碎片和浪费**（而 KV
cache 本身就很大，见第 2 章）。这正是 **PagedAttention（第 4 章）** 要解决的：像操作系统内存分页一样，
把 KV cache 切成固定小块按需分配，消除碎片，让有限显存装下尽量多的并发序列。
