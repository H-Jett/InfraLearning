# 第 1 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 1 章 1.6 思考题》。

## 1. 8 个请求一起 decode，总耗时接近 `1×TPOT` 还是 `8×TPOT`？

**参考答案**：接近 **1×**（远小于 8×）。因为 decode 是访存受限的——权重从显存搬一次，就能被 batch 内
所有序列复用，主要成本（搬权重）被摊薄。这正是 **batching 成为吞吐第一杠杆**的原因。

严谨补充：并非精确 1×。
1. 计算量随 batch 线性增长；但 batch=1 时算力大量闲置，这部分增长近乎"免费"，直到 batch 把算力也填满，
   从 memory-bound 翻转为 compute-bound，此后再加序列才线性变慢。
2. 每条序列的 KV cache 各自独立，attention 段的读取随 batch 增长。

结论：存在一个"甜点 batch size"，超过后收益递减 —— 这引出第 3 章的 continuous batching。

## 2. 为什么 16 token 的 prefill 反而比 256 token 慢？

**参考答案**：这不是"越短越慢"的趋势。16 与 256 都落在**固定开销主导 (overhead-bound)** 区间：
一次前向要发射几十上百个 CUDA kernel + Python 调度，这些开销**与 token 数无关**；而这么少 token 的
实际计算对 GPU 小到可忽略，藏在开销之下。所以该区间总耗时近似**平线**，个别点的高低是噪声/预热抖动，
不是结构性趋势。真正的信号是：per-token 耗时持续暴跌；总耗时要到 token 足够多（如 ≥1024）才随长度真正上升。

教训：**小规模微基准看趋势，别看单点。**

## 3.（进阶）为什么 decode 是访存受限 (memory-bound) 的？

**参考答案**：用**算术强度** (arithmetic intensity = FLOPs / 搬运字节) 判断。矩阵乘 `W·x`：

- **prefill**：一次 N 个 token，算术强度 ≈ N（几百上千）→ 高于 GPU 临界强度 → **compute-bound**；
- **decode**（batch=1）：算术强度 ≈ 1 → 远低于临界强度（约 100~300）→ **memory-bound**。

本质：每生成 1 个 token 都要把整个模型权重从显存完整读一遍，每个权重只用 1 次乘加，算力空转。
**能记一辈子的估算：TPOT 理论下限 ≈ 模型大小 ÷ 显存带宽。**

（注：小模型 + batch=1 时，真正瓶颈往往是 kernel 发射等固定开销，即 launch-bound；见补充 B。）

## 附：其他常见疑问

- **"搬运"是把权重从哪搬到哪？** 从显存 (HBM/GDDR) 经 L2 → shared memory/L1/寄存器 → 计算单元；
  瓶颈精确在"显存 → 片上"这一跳（该链路里显存带宽最低、权重最大）。详见补充 A。
- **HBM 的优势是低延迟吗？** 不是。是**带宽和能效**；单次访问延迟与 GDDR 相当。详见补充 A。
