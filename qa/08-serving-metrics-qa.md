# 第 8 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 8 章 8.8 思考题》。

## 1. 1024 并发原始吞吐最高，为什么 goodput 是 0？启示是什么？

**参考答案**：因为 goodput 只计**满足 SLO** 的吞吐。1024 并发时 TPOT 涨到 30 ms，超过了 SLO（≤25 ms），
所有请求都"超时"——超时的服务对用户没有价值，所以尽管原始吞吐最高（34071 tok/s），有效吞吐（goodput）
记为 0。最大 goodput 反而出现在并发 512（27256 tok/s，此时 TPOT 18.8 ms 仍满足 SLO）。

**启示**：调推理服务的目标**不是最大化吞吐，而是在满足 SLO 的前提下最大化 goodput**。越过延迟拐点
一味加并发，只是在生产"没人要的超时 token"，看着吞吐高，实际有效产出反而降。

## 2. 为什么高并发先伤 TTFT、后伤 TPOT？

**参考答案**：因为两者由不同阶段决定，而这两个阶段进入 compute-bound 的时机不同：

- **TTFT = prefill**。prefill 一次并行处理一批请求的所有 prompt token，本就是 **compute-bound**；
  batch 越大、要算的 token 越多，prefill 越慢，所以 TTFT 很早就随并发上升（19.6 → 156 ms）。
- **TPOT = decode**。decode 每步每条序列只算 1 个 token，是 **memory-bound**；在算力被填满之前
  （本例到并发 512），多加序列几乎不增加每步时间，所以 TPOT 一直稳，直到 1024 才因 compute-bound 跳升。

所以高并发**先**把 compute-bound 的 prefill（TTFT）压垮，**后**才轮到 decode（TPOT）。

## 3. 为什么看 P99 而不是平均延迟？

**参考答案**：因为用户体验和 SLA 由**尾延迟**决定，而平均值会掩盖长尾。

- 平均延迟可能很漂亮，却掩盖了"有一小撮请求慢得离谱"——这批用户体验极差；
- P99 反映"最差的 1% 请求"有多慢，才是 SLO 应该盯的；
- 在多请求串联的系统里（如 agent 调用链、一个页面聚合多个后端请求），**整体快慢由最慢的那个请求决定**，
  一个 P99 慢请求就能拖垮整条链路。

所以定 SLO、评估优化都盯 P99（有时 P999），不看平均。
