## Q1：为什么损失必须对称？

**问题**：CLIP 的损失为什么要对称（图→文 和 文→图 各算一次）？只保留"图→文"会在什么任务上出问题？

**答案**：

因为**检索是双向的**，而单向的 softmax 只约束单向的排序。

- **"图→文"方向**（对相似度矩阵按行做 softmax）约束的是：给定一张图，正确文本要排在所有文本前面。
  它管的是 **image-to-text 检索**（看图找描述）。
- **"文→图"方向**（按列 softmax）约束的是：给定一句话，正确图片要排在所有图片前面。
  它管的是 **text-to-image 检索**（打字搜图）——这恰好是最常见的实际用途。

只保留"图→文"会出的问题：

1. **text-to-image 检索会退化**。因为没人约束"一个文本向量必须离正确图片最近"。
2. **出现 hubness（枢纽点）现象**：某些图像向量会变成"万能匹配"——
   它对很多文本的相似度都偏高。行 softmax 不惩罚这种情况
   （只要在**它自己那一行**里正确文本最高就行），但列 softmax 会立刻惩罚它
   （因为它抢了别的文本的第一名）。**对称损失正是抑制 hubness 的机制。**
3. **两塔的尺度/分布容易失衡**：只优化一个方向时，模型可以靠"把所有文本向量挤到一小块区域"
   来偷懒降低 loss，双向约束让它没法只讨好一边。

顺带一句：这个对称结构后来被 SigLIP 换掉了——它用**逐对 sigmoid** 判断"这对匹配吗"，
天然对称，也不需要在整个 batch 上归一化（见 Q2）。

## Q2：忘了跨卡 all-gather，负样本少多少？

**问题**：batch=32768 时每个 anchor 有多少负样本？8 卡 × 每卡 4096 但**不 gather**，实际是多少？
为什么 CLIP 的这个 all-gather 通信量其实很小？

**答案**：

**负样本数**：

| 情况 | 每个 anchor 的负样本数 |
|------|----------------------:|
| 全局 batch 32768，正确 all-gather | **32767** |
| 8 卡 × 4096，忘了 gather | **4095** |

差了 **8 倍**。后果：

- **难负样本变少**。负样本池越大，池子里出现"难以区分的样本"（比如另一张也是猫的图）的概率越高，
  而 InfoNCE 的梯度**主要来自最难的那些负样本**（softmax 的性质，见第 3.4 节温度那段）。
  池子小 → 大多是易负样本 → 梯度信号弱、判别边界粗糙；
- **实测规律**：CLIP 类模型的效果对 batch size 相当敏感，这也是这类工作普遍报告
  "更大 batch 更好"的原因。（SigLIP 论文的一个重要贡献恰恰是证明了
  **换了损失之后** batch 的边际收益会早早饱和——所以"必须大 batch"是**这个损失函数的性质**，
  不是对比学习的天命。）

**为什么通信量小**：all-gather 的对象是**投影后的特征向量**，不是激活、不是梯度张量。
每张卡 4096 个样本 × 512 维 × 2（图和文）× 2 字节（bf16）≈ **8 MB**。
相比之下把 4096 张图的 ViT 中间激活同步一遍要几十 GB。
所以这里的模式很特别：**通信极小，但对全局 batch 的依赖极强**——
和一般"通信是瓶颈"的分布式训练直觉正好相反。

（工程细节：gather 时要保证梯度能正确回流到本卡的样本，
`torch.distributed.nn.all_gather` 或各框架的 `GatherLayer` 就是干这个的；
用普通的 `dist.all_gather` 会**丢梯度**——这是这类训练里的经典 bug。）

## Q3：softmax 给出 1.000，为什么不能当"100% 确信"？

**问题**：τ=0.01 时输出 1.000。为什么这不是置信度？如果产品要"低于某个匹配度就拒绝"，该怎么做？

**答案**：

**因为这个 1.000 是尺度的产物，不是概率的估计。**

看实测：正确配对的 cosine 是 0.373，最强的干扰项是 0.216，差值 0.157。
乘上 `logit_scale = 100` 之后，logit 差变成 **15.7**——`softmax` 遇到 15.7 的差距必然饱和
（`e^15.7 ≈ 6.6e6`）。同一组相似度在 τ=1 时最高概率只有 0.198，在 τ=0.1 时是 0.601，
在 τ=0.01 时是 1.000。**同一份证据，三种"置信度"**——可见它衡量的是温度，不是信念。

更根本的原因：**CLIP 的训练目标从来不包含概率校准**。
InfoNCE 只要求正确项排第一，不要求"排第一的程度"反映真实正确率。
τ 是为了**优化梯度动态**学出来的，不是为了输出可信概率。

**正确的做法**（按可靠性从高到低）：

1. **只用排序，不用绝对值**：做 top-k 检索、做"哪个类别最像"的比较。
   这是 CLIP 唯一有保证的能力。
2. **要阈值就在你自己的数据上标定**：收一批标注（匹配/不匹配），
   扫 cosine 阈值画 precision-recall 曲线，按业务对 P/R 的偏好取点。
   **注意这个阈值只对"这个模型 + 这套 prompt 写法 + 这个图片域"有效**，
   任何一项变了都要重扫。
3. **需要真概率就做后校准**：在目标域上做温度重标定（Platt scaling / isotonic regression）——
   注意这是**第二个温度**，与 CLIP 内部那个 `logit_scale` 无关，用验证集拟合。
4. **别把 zero-shot 概率接进自动决策链**（自动过审、自动打标签且不复核）。
   本章的例子已经说明：一句"猫站在遥控器上"的错误描述能拿到 0.677。

## Q4：空间关系为什么是结构性缺陷？要判断左右该怎么办？

**问题**：CLIP 把"猫站在遥控器上"排到第一（0.677）。为什么这是结构性的、不是训练不充分？
要判断"遥控器在猫的左边还是右边"，有哪几条路线？

**答案**：

### 为什么是结构性的

回到损失的定义：InfoNCE 要求的仅仅是

> **配对样本的整体相似度 > batch 内其他样本的整体相似度。**

把这个目标和数据分布放在一起看，有三层原因：

1. **负样本几乎全是易负样本**。网页图文数据里，随机抽的另一条数据几乎不可能是
   "同样的词、不同的语序"。要区分"猫在遥控器上" vs "遥控器在猫旁边"，
   模型需要看到大量这种**只差语序的难负样本对**——而它们在自然数据里几乎不出现。
   **没有难负样本，就没有梯度压力**，学不会是必然的。
2. **表示是单个全局向量**。整张图被压成 512 维、整句话被压成 512 维，
   两者只做一次点积。这个瓶颈里**没有位置对齐的容量**：
   模型无法表达"图里区域 A 对应句中词 w1、区域 B 对应词 w2"这种结构。
   词袋级特征（有猫、有遥控器、室内、粉色）就足够把 loss 降到很低了。
3. **文本塔也被这个目标同化**。既然只要词袋特征就能拿分，文本塔就没有动力保留精细的句法结构。
   （ARO 的实验很直接：把 caption 的词序打乱，CLIP 的相似度**几乎不变**——
   它对语序基本不敏感。）

**所以这不是"再多训几轮就好"的问题，是目标函数 + 表示瓶颈 + 数据分布共同决定的上限。**

### 要判断左右，四条可行路线

1. **上 VLM（首选）**：把 patch token 送进 LLM，让 LLM 做关系推理。
   本书后面整个第二部分就是这条路。VLM 之所以能答"左边还是右边"，
   靠的不是 CLIP 变强了，而是**保留了 49（或几千）个带位置的 patch token**
   + LLM 的推理能力。
2. **用带定位监督的模型/数据**：grounding 数据（bounding box + 短语）微调，
   或者直接用支持 grounding 的 VLM（输出坐标框）。空间关系可以从坐标算出来，
   不必指望模型"感觉"出来。
3. **加难负样本重训对比模型**：ARO / NegCLIP 那条线——
   人工构造"同词不同序"的负样本加入训练。有效，但天花板有限（表示瓶颈还在）。
4. **不要用一个模型硬扛**：检测器给出物体框 → 用坐标做规则判断"左/右"。
   在明确的工程任务里，这往往是最稳、最可解释、最便宜的方案。

**选路原则**：需要**开放式描述与推理** → VLM；需要**精确坐标关系** → 检测/grounding + 规则。
把"判断左右"这种确定性任务交给纯对比模型，是选错了工具。
