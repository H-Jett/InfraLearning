## Q1：边长缩一半，token 数为什么掉到 1/4？代价是什么？

**问题**：实测里 1280×960 的图是 1564 个视觉 token，640×480 的图是 391 个。
边长只缩了一半，token 数却掉到 1/4——为什么？为了省 token 就把所有输入图都缩小，
代价是什么？什么场景下这个代价不可接受？

**答案**：

**为什么是 1/4**：视觉 token 数正比于**像素数（面积）**，不是边长。
公式 `tokens = (H/28) × (W/28)` 里高和宽各除一次，边长各缩一半 → 两个因子各减半 → 乘积变 1/4。
实测 1564 / 391 = 4.00，严丝合缝。

推论（很重要的一条工程直觉）：**分辨率是一个二次的成本旋钮**。
边长 ×2 → token ×4 → 注意力计算量 ×16（注意力对序列长度是二次的）。
反过来，稍微降一点分辨率，省下的成本比你直觉估计的多得多。

**代价**：缩图是**不可逆的信息丢失**，丢的正是**高频细节**。
一个 28×28 的像素区域最终只变成一个向量；原图里这块区域如果本来就只有一个色块，
缩不缩无所谓；但如果这块区域里有 3 个汉字，缩完就彻底糊了——模型不是"看不清"，是**根本没收到那些信息**。

**不可接受的场景**（共同点：信息密度高、目标物在图中占比小）：

- **OCR / 文档理解**：小字号文本、表格线、公式上下标；
- **图表理解**：坐标轴刻度、图例小字；
- **细粒度识别与定位**：远处的路牌、UI 界面上的小图标、缺陷检测；
- **高分辨率长图**：网页截图、扫描件。

这正是现代 VLM 从"固定 224×224"走向"动态/原生分辨率"的根本原因（第 8 章）：
让**图片自己决定**要花多少 token，而不是一刀切。

## Q2：patch embedding 为什么就是 Conv2d？stride 改小会怎样？

**问题**：为什么 patch embedding 可以直接用 `nn.Conv2d(3, d, kernel_size=16, stride=16)` 实现？
如果把 `stride` 改成 8（patch 之间重叠），模型会得到什么、又要付出什么代价？

**答案**：

**为什么等价**：卷积的每一次计算，就是"取一个 `kernel_size × kernel_size × 3` 的窗口，
和一组权重做内积"。当 `stride = kernel_size` 时，这些窗口**恰好不重叠、恰好铺满整张图**——
这就是"切 patch"；而"和权重做内积"就是"展平后乘一个矩阵"。
所以 `Conv2d(3, d, k=P, s=P)` 一步同时完成了**切块**和**线性投影**，输出的 `[d, H/P, W/P]`
展平成 `[H/P × W/P, d]` 就是 patch token 序列。本章练习用同一份权重验证过：两种写法数值差异仅 2.32e-06。

**stride=8（重叠 patch）会得到什么**：

- **更密的 token 网格**：224×224 下从 14×14=196 变成 27×27=729 个 token（≈3.7×）；
- **更平滑的边界**：patch 边界不再是硬切，跨边界的小目标/笔画不容易被切碎，
  局部细节表达更好——这类"重叠 patch / 卷积式 stem"在一些视觉模型里确实有用。

**代价**：

- **序列长度 ×3.7 → 注意力计算量 ×13.7**（二次关系），显存和延迟同步恶化；
- **信息冗余**：相邻 token 覆盖的像素大量重合，边际信息量低，等于花 4 倍成本买一点点收益；
- **与主流预训练权重不兼容**：CLIP/SigLIP 等现成视觉塔都是不重叠切分，改了就没法复用权重。

结论：主流 VLM 不但**不会**减小 stride，反而在拼命往**反方向**走——
Qwen2-VL 系列的 2×2 merge 把 4 个 patch 合成 1 个 token，就是嫌 token 太多。
在"token 预算"这个约束下，重叠 patch 属于买椟还珠。

## Q3：32 路并发的 KV cache 显存账

**问题**：并发 32 路请求，每路一张 960×686 的图 + 200 token 文本提示。
光 KV cache 要多少显存？换成 1080p 原图呢？

**答案**：

用本章的实测数字：Qwen2.5-VL-3B 每个 token 的 KV cache = 2 × 36 层 × 2 个 KV 头 × 128 × 2 字节 = **36 KiB**。

| 场景 | 每路 token 数 | 每路 KV cache | ×32 路 |
|------|--------------:|--------------:|-------:|
| 960×686 + 200 文本 | 816 + 200 = 1016 | 35.7 MiB | **1.12 GiB** |
| 1920×1080 + 200 文本 | 2691 + 200 = 2891 | 101.6 MiB | **3.18 GiB** |

（以上只算 prefill 结束时的占用，还没算生成过程中不断追加的 output token。）

**怎么看这两个数**：

- 1.12 GiB 不算什么——**3B 模型本身 bf16 权重就要约 7 GiB**（3.75B 参数）。
  所以在这个量级下，KV cache 不是主要矛盾。
- 但注意**趋势**：换成 1080p，KV cache ×2.8。如果再把并发提到 128、
  或者换成 72B 的模型（层数和 KV 头都多几倍），这个数字会迅速逼近甚至超过权重本身。
  KV cache 随 **并发 × 序列长度** 线性增长，而视觉 token 让"序列长度"这一项凭空多了一个数量级。

**真正先爆的往往不是 KV cache，而是这两个**（诚实说明，这也是 VLM 和纯文本 LLM 的差别）：

1. **prefill 计算量**：32 × 2891 ≈ 9.2 万 token 要一次性算完，TTFT 直接被拉长；
2. **视觉塔的激活显存**：ViT 处理 32 张 1080p 图时的中间激活是**峰值显存**的主要来源之一，
   而且它和 LLM 的 KV cache 是**同时**存在的。

**怎么回应"要支持 1080p 原图"**：这不是一个"能不能"的问题，而是"用什么换"的问题。可选的牌：

- **调 `max_pixels`**：给不同业务设不同的 token 上限，让成本可控（最直接的旋钮）；
- **按任务分流**：OCR/文档类走高分辨率，普通图文问答走低分辨率；
- **降并发或加卡**：把 SLO 和成本摊开算给对方看；
- **上 token 压缩**：merge / 剪枝，用少量精度换 token 数（第 11 章）。

关键是把"1080p"翻译成"每张图 2691 个 token、每路 100 MiB KV cache、TTFT +X ms"这样的具体数字，
让讨论从偏好之争变成成本核算。
