# 第 5 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 5 章 5.7 思考题》。

<a id="q1"></a>

## 1. 为什么短前缀（256/1024）时前缀复用几乎没收益、甚至略亏？

**参考答案**：回到第 1 章——**短 prompt 的 prefill 本就是 overhead-bound（固定开销主导）**，
耗时几乎是一条平线（~19 ms），因为一次前向发射几十上百个 kernel 的固定开销盖过了这点计算量。
既然重算这段短前缀本来就没花多少时间，跳过它自然省不出东西；而前缀复用还要多一点点管理缓存、
准备复用的开销，于是净收益 ≈ 0 甚至略负。

只有当前缀长到脱离 overhead-bound、进入 **compute-bound**（本例 ≥4096），被跳过的那段 prefill
才真的很贵，前缀复用才有可观收益（4096→2.7×，16384→7.2×）。

**要点：前缀复用的收益 = 被跳过的 prefill 是否真的贵，而不是"共享了就一定省"。**

<a id="q2"></a>

## 2. 为什么多轮对话是前缀复用的完美场景？

**参考答案**：因为第 N 轮的 prompt = **前 N-1 轮的全部历史 + 新消息**，其中"历史"部分和第 N-1 轮
**完全重叠、且逐轮越来越长**。

- 前缀完全匹配：历史是从第 0 个 token 起逐 token 相同的真前缀，天然可复用；
- 前缀越来越长：对话越深，共享前缀越长 → 每轮省下的 prefill 越多，正好落在收益最大的区间；
- 若不复用，每轮都要把越来越长的历史重新 prefill 一遍，代价随轮数快速膨胀。

所以多轮长对话下，前缀复用几乎是必备优化。

<a id="q3"></a>

## 3. 为什么"树"特别适合"很多请求共享不同长度前缀"？

**参考答案**：因为 radix / 前缀树的结构天然表达"共享前缀"：

- **一条路径 = 一段 token 序列**：从根往下走的路径就是某请求的前缀，公共前缀自然对应**共享的同一段路径**；
- **分叉点 = 前缀开始不同的地方**：多个请求在某处 token 不再相同，就在树上分叉——分叉点之前的路径
  （及其 KV）被共享，之后各走各的；
- **自动最长匹配**：新请求进来，沿树往下走到不能再匹配为止，走过的路径就是可复用的最长公共前缀，
  无需预先约定前缀边界，能处理**任意长度、任意组合**的共享；
- **LRU 淘汰叶子**：显存不足时从最久未用的叶子往回删，天然契合树结构。

相比之下，vLLM 的哈希块方案对"整段相同前缀"很有效，而树结构把它泛化到了任意请求间的任意公共前缀。
