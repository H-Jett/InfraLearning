# 第 7 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 7 章 7.8 思考题》。

<a id="q1"></a>

## 1. 为什么"验证 16 个 token 只比 1 个多约 3ms"让"先猜后验"划算？

**参考答案**：因为目标模型的一次前向是**访存/发射受限**的——成本主要花在把权重从显存搬一遍，
而不是算多少个 token。所以一次并行验证 K 个 token 的总耗时几乎和验证 1 个一样（16.78 ms → 19.71 ms，
K 从 1 到 16）。既然"多验几个几乎免费"，那就先用便宜的草稿模型猜出 K 个 token，再让目标模型一次性
验证——一次目标前向就能收获多个 token，而目标前向的次数正是 decode 慢的根源。这等于用空闲的算力
（沿序列方向"批处理"验证）换掉了一部分昂贵的、串行的目标前向。

<a id="q2"></a>

## 2. 投机解码靠什么保证"无损"？

**参考答案**：靠一套**接受/拒绝采样**。对每个草稿 token，设草稿给它的概率是 q、目标给它的概率是 p，
就以 min(1, p/q) 的概率接受；一旦拒绝，就从修正后的分布（(p−q) 的正部分归一化）重采样一个 token。
可以从数学上证明：这样产生的序列分布**严格等于目标模型自己逐 token 采样的分布**。

所以投机解码只改变"生成的路径/速度"，不改变"生成的分布"——质量和目标模型直接解码完全一致，是**无损**加速。
这与量化、剪枝等会引入误差的"有损"手段有本质区别。

<a id="q3"></a>

## 3. 为什么高并发（大 batch）时投机解码收益大幅缩水？

**参考答案**：投机解码的红利来自"目标模型验证 K 个 token 几乎免费"，而这个前提是目标模型处于
**memory-bound**（算力闲置，多验几个不加钱）。

但由第 1、3 章：**高 batch 下目标模型已经 compute-bound**——GPU 算力被一大批序列喂饱了。这时再让它
一次多验 K 个 token，就要实打实地多花计算时间了，"免费验证"不再免费，投机解码的加速自然大幅缩水。

因此投机解码主要用在**低延迟、低并发**场景（如单用户交互，此时目标 memory-bound、算力有富余）；
而高吞吐、高并发的离线场景，提速主要靠 batching 而非投机解码。二者的适用区间正好互补。
