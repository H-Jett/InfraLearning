# 第 6 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 6 章 6.9 思考题》。

<a id="q1"></a>

## 1. fp32→bf16 显存精确减半，为什么速度几乎没变？什么时候量化才提速？

**参考答案**：因为 0.6B 小模型 + batch=1 的 decode 是 **launch-bound**（卡在 kernel 发射等固定开销），
**不是显存带宽受限**。既然瓶颈根本不在"搬权重"，把权重字节减半也救不了速度——但显存实打实省了一半。

**量化真正加速 decode 的条件**：decode 必须是 **bandwidth-bound（访存/带宽受限）**。由第 1 章公式
`TPOT 下限 ≈ 模型字节 / 带宽`：大模型（如 70B，bf16 下限 ~78ms）decode 就卡在带宽上，这时把权重
压到 int4（字节 1/4）→ decode 下限也降到约 1/4（~19ms），接近线性提速。小模型下限 <1ms ≪ 实测，
瓶颈是发射开销，降精度不提速。

**一句话：省显存永远成立；提速只在 decode 卡带宽时才有。**

<a id="q2"></a>

## 2. 要提升最大上下文 / 并发，量化权重还是 KV cache？

**参考答案**：优先量化 **KV cache**。

因为限制"最大上下文 / 并发数"的是 **KV cache 显存**（第 2 章：随 seq_len 和 batch 线性增长，长上下文/
高并发时它是头号显存杀手）。量化 KV cache 直接砍第 2 章公式里的"每元素字节"（bf16→int8 即 2→1），
KV cache 减半 → 同样显存能塞约 2× 的并发或 2× 的上下文长度。

量化权重省的是"权重那份固定显存"，对"能同时服务多少长序列"帮助有限——权重是一次性的，不随并发/长度
增长。所以针对 KV 吃紧的瓶颈，量化 KV cache 才对症。

<a id="q3"></a>

## 3. weight-only（W4A16）主要加速哪个阶段？为什么对另一个帮助不大？

**参考答案**：主要加速 **decode**（且是大模型的 decode）。

- **decode 是访存受限**：每步都要把整个模型权重从显存搬一遍。weight-only 把权重压成 int4，加载的
  字节少了约 4×，大模型 decode 因此按比例提速。
- **prefill 帮助不大**：prefill 是 **compute-bound**，而 W4A16 计算时把权重**反量化回 fp16 再算**，
  实际算力精度没变（还是 fp16 GEMM），所以计算没变快；反而多了反量化的开销。要加速 prefill 得让
  **计算本身**用低精度（W8A8 + int8 Tensor Core），那是另一条路线。
