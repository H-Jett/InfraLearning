# 第 11 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 11 章 11.5 思考题》。

<a id="q1"></a>

## 1. 随机访问比顺序访问慢约 5 倍，数据量一样，慢在哪一步？

**参考答案**：慢在**内存事务**上，不是数据量上。同一 warp 的 32 个线程一起发访存请求：
- **顺序访问**：32 个地址是连续的一段，硬件把它们**合并成一次大内存事务**，一次搬回一整块，带宽利用率接近 100%；
- **随机访问**：32 个地址散落各处，无法合并，退化成**很多次小事务**，每次只搬回其中很小一部分有用数据，
  大量带宽浪费在"为零散地址各跑一趟"上。

所以搬的总字节数一样，但随机模式的**有效带宽**只有顺序的 ~1/5（实测 1594 → 288 GB/s）。这就是访存合并。

<a id="q2"></a>

## 2. 一个 memory-bound、访问跨步的 kernel，有哪两类改善思路？

**参考答案**：
1. **改数据布局 / 改映射，让访问变连续**：调整数组的存储顺序（如行主序 vs 列主序），或改变
   "哪个线程处理哪个元素"的映射，使**同一 warp 的相邻线程去访问相邻内存**，把跨步变成合并访问。
2. **用 shared memory 中转**：如果访问模式天生躲不开分散（如转置、gather），就让 block **先把需要的数据
   以合并方式整块读进 shared memory**，再在片上按任意（分散）顺序使用——把"对 HBM 的分散访问"换成
   "对 HBM 的合并访问 + 对片上内存的分散访问"，而片上内存分散访问代价小得多。

<a id="q3"></a>

## 3. tiling 为什么能让 memory-bound 算子变快？往 roofline 哪个方向推？

**参考答案**：因为 tiling **减少了对 HBM 的访问次数**。把一块数据从 HBM 载入 shared memory 一次后，
block 内线程在片上**反复复用它很多次**，而不是每次计算都回 HBM 读。于是**同样的计算量，搬运的字节数
大幅下降** → **算术强度（FLOP/byte）升高**。

用第 10 章的 roofline 语言：算术强度升高 = 在横轴上**往右移**，从"带宽屋顶"下的 memory-bound 区，
往拐点右侧的 compute-bound 区推。一旦推过拐点，瓶颈就从"搬数据"变成"算"，算力才被真正用满。
这正是矩阵乘、FlashAttention 等算子优化的核心思路。
