# 第 10 章 · 思考题参考答案

> 只记录问题与参考答案。对应正文《第 10 章 10.7 思考题》。

<a id="q1"></a>

## 1. bf16 矩阵乘比 fp32 快 3.5×，靠什么？

**参考答案**：两个原因叠加：

1. **用了 Tensor Core**：bf16 矩阵乘走的是专门的矩阵乘单元（一条指令做一小块矩阵乘加），
   吞吐远高于普通 CUDA core 的标量乘加；fp32（关 TF32）只能用 CUDA core。
2. **精度更低、字节更少**：bf16 是 2 字节 vs fp32 的 4 字节，搬运和存储都减半，对带宽也更友好。

主因是 Tensor Core，其次是低精度。（实测 fp32 67 → TF32 114 → bf16 237 TFLOPS，能看出"上 Tensor Core"
和"再降精度"各贡献一段提速。）

<a id="q2"></a>

## 2. 算术强度 10 FLOP/byte，在拐点 ≈151 的 5090 上是哪种 bound？怎么提速？

**参考答案**：10 < 151 → **memory-bound**（远在拐点左侧，卡在带宽）。

提速方向：**不是"提高算力"**（算力本来就没用满），而是**减少访存 / 提高算术强度**：

- **算子融合 (fusion)**：把多个逐元素算子合并成一个 kernel，中间结果不落显存，一次读写算更多 →
  算术强度上升、访存下降；
- 减少要搬的字节（如低精度）；
- 提高数据复用（tiling，把数据留在 shared memory 里多次用）。

把算术强度推过拐点，才轮到算力成为瓶颈。这也是第 13、14 章算子优化的核心手段。

<a id="q3"></a>

## 3. （Brent）顺序累加 vs 树状归约，谁更快？加速上限由 work 还是 depth 决定？

**参考答案**：给足够多核，**树状归约更快**。

- 顺序累加：work W=N-1，但**依赖链 depth D=N-1**（每步依赖上一步的结果），再多核也得一步步走 → O(N)；
- 树状归约：两两相加、层层折半，work 还是 ~N，但 **depth D=log₂N** → 给足够核可达 O(log N)。

由 Brent 定理 `T_p ≥ max(W/p, D)`：当核足够多、W/p 很小时，运行时间被 **depth D** 锁死。所以**并行加速
的上限主要由 depth（最长依赖链）决定，而不是 work**。写并行 kernel 的关键就是**压低 depth**——
这正是第 14 章手撕 reduction 要做的事。
