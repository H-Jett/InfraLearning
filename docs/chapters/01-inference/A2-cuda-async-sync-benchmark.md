# 补充 B 　CUDA 的异步执行、同步与正确的基准测试

> 第 1 章的练习脚本里，前前后后加了不少 `torch.cuda.synchronize()`。这不是多余，
> 而是"在 GPU 上准确计时"的必备功课。本节讲清楚它背后的机制。

## B.1 CPU 与 GPU 是"老板与员工"

在 **CUDA**[^cuda] 编程里，可以把两者想成：

- **CPU 是老板**：负责发号施令（把计算任务下发给 GPU）。
- **GPU 是员工**：负责埋头干活（真正执行计算）。

关键在于两者是**异步 (asynchronous)**[^async] 的：老板把任务书（一个 **kernel**[^kernel]，
即 GPU 上的一个计算任务）往员工桌上一扔，**不等员工开始做，就立刻转头去干别的**。
指令发射出去后，CPU 这边的函数马上就返回了。

## B.2 为什么不同步，测速会错

正因为异步，下面这段"看起来没问题"的计时是**错的**：

```python
t0 = time.perf_counter()
out = model(x)                 # 只是把 kernel 发射出去，GPU 还没算完就返回了
t1 = time.perf_counter()       # 这里测到的几乎只是"发射耗时"，几微秒
```

`t1 - t0` 测到的是"老板扔任务书"的时间（几微秒），**不是"员工把活算完"的真实耗时**。
要测真实耗时，必须在掐表前，强制 CPU 等 GPU 把活干完。

## B.3 `torch.cuda.synchronize()` 到底是什么

它是一个**屏障 (barrier)**[^sync]，不是"启动 GPU"的信号——这点最容易误解：

- 它做的事：**CPU 走到这行必须停下，盯着 GPU，直到 GPU 把已排队的任务全部算完，才放行。**
- 它不做的事：它**不会**去"催"或"启动"GPU；GPU 早在 kernel 发射时就开始干了。

> **老师提问**：如果前面根本没有 GPU 任务，调用 `synchronize()` 会不会卡死？
> **答**：完全不会。它就像一个无人的检查站——CPU 问一句"还有活没干完吗？"，得知没有，
> 就零延迟直接通过。同步只等"已排队但没算完"的活，没有活就立即返回。

## B.4 一个"满分"基准测试的三要素

理解了上面，就明白第 1 章练习里的计时套路为什么这么写。三个要素缺一不可：

1. **预热 (warmup)**[^warmup]：GPU 第一次跑某个算子有冷启动开销（显存分配、kernel 编译/缓存等）。
   先空跑几次把这些一次性开销甩掉，再正式计时。
2. **前置 `synchronize()`**：在 `t0` **之前**同步一次，结清"陈年旧账"——确保开始计时时，
   GPU 里没有上一段残留的任务在跑，否则它们会赖到本次的账上。
3. **后置 `synchronize()`**：在 `t1` **之前**同步一次，强制 CPU 等本次任务真正算完再掐表。

对应到练习脚本 `01_prefill_vs_decode.py` 里的 `timeit()`：先 warmup，再对每次测量
"前 `sync()` → 计时开始 → 跑 → 后 `sync()` → 计时结束"，最后取多次的中位数以抗抖动。

## B.5 更精细的并发：CUDA 流 (Streams)

`torch.cuda.synchronize()` 会**一刀切地等待当前设备上的所有任务**。但有时我们想让多个任务
并发，只等其中一部分，这就要用 **CUDA 流 (stream)**[^stream]——可以理解为 GPU 里的"多条车道"：

- 同一条流内的任务按提交顺序依次执行；
- 不同流之间可以**并发**。

于是有了粗细两种同步：

| 同步方式 | 作用 | 场景 |
|---|---|---|
| `torch.cuda.synchronize()` | 全设备红灯，等所有流 | 最安全，但最影响并发 |
| `stream.synchronize()` | 只等当前这一条流 | 想让别的流继续跑，做**计算与通信重叠 (overlap)** |

"计算与通信重叠"在分布式训练里尤其重要：一条流算梯度，另一条流用 **NCCL**[^nccl] 传梯度，
两者并发，把通信时间藏到计算背后——这点我们会在第二部分（分布式训练）细讲。

---

**本节一句话**：硬件（带宽）决定模型能跑多快的**上限**；而对异步执行的正确控制
（同步 / 流）决定你能不能**准确测量**、以及能把硬件潜力压榨出几成。
